## 验证证据

各阶段均运行项目统一门禁 `./scripts/run_all_tests.sh`；现有 89 个 CTest 分组继续承载新增回归，无新增测试执行文件。

- 第一阶段：空 JSON 诊断、审核回退、乱序/重复请求、跨请求候选隔离、向量维度错误。
- 第二阶段：嵌套/跨字段错误在 Validator 与初始化中一致拒绝；真实 Pipeline 证明未连接输入无法读取无依赖生产者的默认键。
- 第三阶段：JavaScript 操作生成的 Pipeline 由原生 Validator 通过；Chromium 实际创建模型、拖动端口连接、执行校验，无页面异常。
- 第四阶段：5000 字节 DocQA 结果在可变长出口完整保存，旧 C ABI 仍按原数组容量拒绝；真实 Operator 输出超过旧 2048 字节限制时成功，池不足时回滚且能复用唯一租约。
- 第五阶段：小文件测试覆盖权重/sidecar 损坏、缺失、路径变更；实际 DocQA 与 Whisper 资产散列通过；完整 CPU 构建和实际编译的 minimal 工具通过对应变体检查；浏览器验证资产表单与验收状态显示。
- 关键词业务的 [实际验收记录](rfcs/reviews/0037-keyword-acceptance.json) 标注 4 条样本，所选字段精确匹配 4/4；方案或验收输入改变后旧记录失效。测试还验证缺失样本和错误结果不能通过。

## 收益与使用建议

最直接的收益是前三个正确性边界及 Operator 容量修复：防止错误成功与串请求，并消除已有池容量无法使用的问题。表单与资产组合减少重复填写模型参数；原生校验和执行证据能让选择有据可查。

同一外部契约的新业务方案，现在优先通过 JSON/Studio 完成；全新宿主结构的接入，仍需在 Layer 1 完成输入转换、一次结果映射，以及必要的外部内存类型注册。没有为了减少文件数而删除这些边界。详见 [最短接入路径](BUSINESS_ONBOARDING.md)。

模型与 Backend 的选择方法、命令和状态含义见 [可验证选择指南](VERIFIABLE_SELECTION.md)。本次不包含吞吐或人力节省比例的基准测量，因此不声称具体加速倍数。

## 明确保留的边界

- 普通资产检查通过只表示配置、文件身份和编译能力通过；`ready_for_business` 还要求匹配的实际效果记录。
- 已实际标注验收的业务仅关键词 4 条样本。LLM、OCR、ASR、Embedding/Rerank 的业务质量需要各自目标数据集，不能从 smoke 成功推导。
- Kite 构建选择规则已提供，未把当前默认 CPU 构建当作 Kite 硬件验收；内网 SDK、真实目标设备迁移与接受测试仍按 RFC-0029 执行。
- 本轮按用户指定五项收敛。原审计中的其他条目，例如多节点 Control 更新原子性，并未因此自动关闭；这份记录不代表仓库全部 P1/P2 清零。
