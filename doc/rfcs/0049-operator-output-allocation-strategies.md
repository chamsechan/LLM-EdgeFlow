# RFC 0049: Operator 多输出与可注册的单份分配方案

- **RFC 编号**：0049-operator-output-allocation-strategies
- **创建日期**：2026-09-11
- **文档状态**：Completed
- **关联分支**：`feat/operator-output-allocators`
- **目标版本**：v10.x
- **负责人 / 作者**：LLM-EdgeFlow contributors
- **关联决策**：补充 RFC-0009、RFC-0046；替代单业务只允许一个输出池的限制

## 1. 问题与范围

一个 Operator 可以返回多个命名输出。相同 map 键和外层 C 结构也可能因配置而需要
不同的嵌套 `void*` 载荷。当前实现只接受一个输出槽位和一份 `data.mem_que`，且
具体类型注册位于接入层私有头中，不能以独立源码扩展注册同一外层类型的多种分配方案。

本次范围为接入适配层 / Integration、部署解析工具与验证。公共 C ABI、内部 Node
端口与算法保持现有契约；不接入真实公司 SDK，不增加生产业务或推测其结构定义。

## 2. 决策与权衡

- 分开表达输出槽位、外层类型、分配方案及其参数。`type` 仍匹配 bridge 声明的外层
  ValueType；可选 `allocator` 选择为该类型注册的实现，`params` 保存实现校验并补齐
  的单份分配参数。map key 本身不选择嵌套布局。
- 源码扩展头公开 ValueType 描述和注册函数，以及命名输出分配方案的注册函数/宏；
  注册表、池深度、租约与队列实现继续留在接入层内部。方案与外层结构类型不兼容、
  重复注册或注册冻结后的写入均拒绝。参数规范化由选中的实现负责。
- 配置阶段将 JSON 参数解析为方案自己的不可变 `OutputAllocationParameters`，
  分配、重置和单份载荷预算回调共享该对象；bridge 输出转换也接收该配置。
  JSON 留在解析及工具序列化边界，不在输出池分配/析构路径复制或销毁 JSON。
  分配器只创建一个根结构及其嵌套存储，通过 `OwnedExternalBlock` 持有清理
  动作；不得保存调用请求或管理输出队列。清理记录使用匹配分配方式的删除函数，
  部分分配失败自动回滚。
- 新增 `data.outputs`，按 bridge 的逻辑输出槽位配置独立的类型、分配方案、参数和
  容量。与旧 `data.mem_que` 互斥。每个已声明槽位必须有配置，包括可选输出。
- 输出槽位可以显式指定 map key 后缀，默认沿用类型后缀；逻辑槽位和有效 key 后缀
  分别唯一，允许不同槽位复用外层类型和分配方案。各槽位的输出池独立，25 的默认
  深度只由框架应用。逐槽位计算并累加整个 handle 的载荷预算。
- 每个输出槽位可注册自己的结果转换回调；已有单输出 bridge 继续复用原回调。
  新的多输出 bridge 必须逐槽位提供转换，避免把一个裸指针按不同结构误解。
- Process 在所有输出转换成功后才发布结果；任一输出失败时归还已获取的全部租约。
  每个槽位按 batch 顺序获取自己的独立池，不因复用同一类型增加单池需求。

通用代码不推断任意 `void*` 指针树。新布局的枚举、容量、递归边界和释放规则由该
类型的实现负责；配置仅在 Create 解析，不允许 Process 中切换已预分配块的布局。

## 3. 兼容与迁移

已有单输出 `.conf` 和 bridge 保持行为；未指定 `allocator` 时使用 ValueType 默认
实现，未声明参数处理器时拒绝非空 `params`。源码扩展描述符增加字段后须重新编译，
公开 Operator 函数表及 C 结构保持不变。

`resolve-conf` 对新配置报告每个输出槽位的有效分配方案和参数，保留已有单输出
`output_pool` 结果。现有 Demo/Studio Profile 仍使用原单输出业务，不新增 UI 流程。

## 4. 验证与完成条件

- 已有单输出行为和配置兼容；多输出、复用类型但不同槽位/容量均正确解析和执行。
- 相同 map key、相同根结构在不同 handle 配置下选择不同已注册实现；嵌套枚举、
  存储和转换匹配，未知方案、类型不匹配和非法参数在分配前拒绝。
- 清理覆盖部分分配失败、多输出转换失败及成功后的租约复用；释放无泄漏或重复。
- 注册冻结与冲突检查；全 handle 预算按不同方案和槽位累加。
- 扩展现有 Operator 套件并运行相关 sanitizer 检查；完成一次
  [canonical gate](../../CONTRIBUTING.md#6-run-one-canonical-delivery-gate)。

## 5. 实施与最终结果

已实现源码扩展注册、逐槽位部署解析、独立输出池与转换，以及 `resolve-conf` 的
有效参数展示。具体接口与参与编译的嵌套指针示例见
[输出分配方案](../dev_guide/operator_output_allocation.md)。

分配失败验证发现 JSON 的复制和析构不适合输出池生命周期，因此最终实现只在配置
阶段解析 JSON，并在池中共享类型化、不可变的参数对象；归还和重新获取输出不分配
内存。独立测试已验证所有现有输出类型和新增嵌套类型的逐次分配失败回滚、两个
handle 使用相同输出键但选择不同方案、多输出失败后的完整回滚及重试、总载荷预算。
参数规范化本身的分配失败也有独立的无泄漏和重试检查。

默认构建的 Operator API、输出池和值类型注册套件已通过；旧配置与新 `data.outputs`
的解析结果一致，原关键词 Demo 的四条结果符合预期。独立 Debug ASan/UBSan 构建
开启泄漏检测，五个 Operator 套件通过：95 项通过，两个依赖 ONNX 的用例因该构建
关闭后端而跳过；这些用例由默认后端构建覆盖。未发现 sanitizer 或泄漏报告。

默认后端集、全部 CTest、格式与文档检查通过统一的 `./scripts/run_all_tests.sh`
交付门禁验证。本次不涉及真实公司 SDK 或新增模型效果验收。
