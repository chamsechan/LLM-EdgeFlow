# RFC 0029: 外网架构收口与内网 SDK 迁移分阶段整改

- **RFC 编号**：0029-external-readiness-and-intranet-sdk-migration
- **创建日期**：2026-09-02
- **文档状态**：In Implementation
- **关联分支**：`refactor/external-readiness-layer-boundaries`
- **目标版本**：v10.x（外网准备）/ 内网接入版本待定
- **负责人 / 作者**：LLM-EdgeFlow Team

## 1. 背景与动机

2026-09-02 架构审计记录了正式交付、构建边界和维护性问题；RFC-0028 已关闭其中三个
发布阻断项以及 Session、Catalog 两项运行时风险。剩余工作既包含可在当前环境完成的
交付准备，也包含只能在公司内网完成的专有 SDK 集成与目标硬件验收。若不显式区分，
后续演进容易把环境限制误判为实现缺陷，或者在没有真实契约时臆造内部 SDK 接口。

### 1.1 已确认的环境边界

当前仓库所在的外部开发环境不能访问公司内部 SDK。开发者和自动化代理不得要求用户
把内部 SDK、头文件、二进制、模型、配置或凭据提供到此外部环境。只有把整个项目迁移
到经授权的公司内网后，才能读取真实 SDK 契约、实现集成并执行目标硬件验收。

这是一项持续有效的合规与环境约束，不是临时缺失文件，也不能通过猜测接口、制作带有
专有名称的伪 SDK 或降低验收标准来绕过。

### 1.2 “SDK”术语边界

- **本项目交付 SDK**：由本仓库构建的 `libcompany_alg_sdk` 与现有公共头。当前阶段只保持
  现有构建和 ABI 契约；安装、打包、仓库外消费及迁移布局随真实内网交付契约再设计。
- **公司内部 SDK**：只能在内网获得的专有依赖。其接口、运行时、模型和硬件行为在当前
  环境均未知，必须延期到内网阶段验证。

### 1.3 目标

1. 当前阶段完成不依赖内部 SDK 契约的编译边界与中立契约收口。
2. 保持内部 SDK 接入点业务中立、供应商类型不外泄，并为内网接入准备明确清单。
3. 把审计剩余架构债务排入有依赖关系的后续整改，不以一次性大重构阻塞迁移。
4. 对当前可验证与必须延期的证据分别签发，禁止提前宣称内部 SDK 或生产环境已验收。

## 2. 设计范围与边界

### 2.1 当前外网阶段范围

- 建立能表达四层依赖方向的编译 target、轻量 contracts/SPI 与 Composition Root。
- 将业务 Blackboard keys 从 Layer 2 中立契约移至 Layer 1 Adapter 所有权。
- 保留现有 `3rdparty/` 本地持久缓存方案，并增加缓存兼容元数据与 fail-closed 校验。
- 保持现有开源 Backend 与测试替身可用，不引入任何内部 SDK 假实现。
- 仅顺带处理能降低上述变更风险的维护性和治理问题。

### 2.2 内网阶段范围

- 在具备真实文档、头文件、库、目标工具链和硬件后，先识别内部 SDK 所属责任层。
- 根据内网真实交付契约再设计本项目 SDK 的 install/export、仓库外消费和迁移证据包，
  不在外网阶段预设目录、包管理或运行时依赖布局。
- 通过内网包管理或显式 CMake package/path 接入专有依赖，不把供应商类型扩散出具体
  Backend 或 Adapter。
- 使用真实模型和目标硬件完成正确性、并发、容量、性能、长稳和故障注入验收。
- 在内网仓库建立专项 RFC/验收记录，补齐当前外部环境无法获得的证据。

### 2.3 非目标

- 当前阶段不实现、模拟或推断公司内部 SDK 的任何具体接口。
- 当前阶段不实现本项目 SDK 的 install/export/package、仓库外消费示例或迁移证据包。
- 不把内部 SDK、模型、配置、凭据或内部文档提交到此外部仓库及其远端历史。
- 不因未来 SDK 接入修改现有 C ABI、Operator 签名、业务结构体或 Pipeline Schema。
- 不把目录拆分、文件行数下降或测试搬迁本身当作生产就绪证据。
- 不在单个 PR 中同时完成交付打包、四层 target graph、业务键迁移和内部 SDK 接入。

### 3.1 推荐顺序

1. 先完成 RFC-0030（ARCH-001），再完成 RFC-0031（ARCH-002）。
2. 保留现有 `3rdparty/` 方案，只补充缓存来源和 ABI 兼容性校验。
3. 整个项目进入授权内网且满足重启条件后，再设计 EXT-001 至 EXT-004，并依次执行
   INT-001、INT-002、INT-003。
4. MAINT-001 仅在能降低正在修改区域风险时顺带实施，避免无业务收益的大规模搬迁。

## 4. 内网接入的架构路由

内部 SDK 的真实能力未知，进入内网后必须根据可执行契约分类，不能从名称推断：

- 若 SDK 提供设备运行时、图执行、张量 I/O 或模型加载资源，归入 Layer 4 具体 Backend；
  供应商头和类型不得越过该 Backend。
- 若 SDK 定义平台 C/Operator 输入输出、所有权或业务 DTO 转换，归入 Layer 1 Adapter 或
  Operator bridge；六个 `Alg_*` 入口继续保持 C11、`noexcept` 和双 catch 屏障。
- 模型预处理、后处理和 capability 语义仍由 Layer 4 Model 拥有，不塞入 Backend。
- Layer 2 Pipeline/Validator 和 Layer 3 通用 Node 默认不因供应商 SDK 修改；只有 Catalog
  和真实需求证明中立能力缺口后，才按所属层另立 RFC。

依赖方向始终保持 Layer 1 → Layer 2 → Layer 3 → Layer 4，组合和注册由上层
Composition Root 负责，不能在中央 dispatch switch 中增加内部业务分支。

## 5. 关键不变量与重启条件

### 5.1 持续不变量

1. 外部仓库不得出现公司内部 SDK 或受限资产，也不得出现根据猜测编写的专有接口。
2. 本项目交付 SDK 与公司内部 SDK 必须使用完整术语区分，避免验收对象混淆。
3. v10 当前正式动态导出面仍是 RFC-0028 冻结的 12 个入口；变更需独立兼容性 RFC。
4. 外网测试成功只证明本项目、开源 Backend 和测试替身，不证明内部 SDK 或目标硬件。
5. 内网专项证据不能被外网 mock、静态分析或相似开源运行时替代。
6. 每个阶段使用独立提交/PR 和自己的验收证据；历史审计报告保持时间点记录。

### 5.2 内网工作重启条件

只有同时满足下列条件，才能把 INT-001 从“延期至内网”改为实施中：

- 完整项目已经迁入经授权的公司内网仓库或工作区；
- 开发人员获准访问真实 SDK 文档、头文件和库；
- 目标编译工具链、运行硬件和驱动可用；
- 正式模型、Pipeline/config 和测试数据具有合规访问路径；
- 产品方在测试前给出容量、延迟、吞吐、内存和稳定性验收阈值。

条件未满足时，后续贡献者应继续处理 vendor-neutral 的外网整改项，并记录延期状态；
不得再次要求把内部资产带到外部环境。

## 6. 验证与验收计划

### 6.1 外网阶段证据

- 构建四层 OBJECT targets、Composition Root、现有 SDK、CLI、Demo 与测试 runner。
- LayerGuard 校验 source ownership、依赖方向、业务 key 所有权和轻量计划 include。
- Adapter、Blackboard、Validator、Catalog、全部业务 Pipeline 与现有 ABI 契约测试通过。
- 缓存元数据自测覆盖缺失、匹配和篡改三种状态；完整构建归档各依赖指纹。
- 每个实现 PR 最后运行一次 `./scripts/run_all_tests.sh`。

### 6.2 内网阶段证据

- 内部 SDK package discovery、链接、加载失败和版本不兼容必须 fail-closed。
- 具体 Backend/Adapter 增加最小单元、契约和异常测试，并通过 Catalog/Definition 审计。
- 对每个正式 Pipeline 执行真实模型端到端测试，检查 batch 边界和
  `(req_id, sub_id)` provenance。
- 在目标硬件上记录冷启动、稳态吞吐、p50/p95/p99 延迟、峰值内存、并发和长稳结果。
- 执行 SDK 初始化失败、模型损坏、资源不足、超时及进程生命周期故障注入。
- 运行内网 canonical gate，并出具明确区分通过项、限制和未覆盖范围的专项验收报告。
