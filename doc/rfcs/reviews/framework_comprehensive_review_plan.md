# LLM-EdgeFlow 框架全面审查方案

## 1. 文档定位

本文定义对 LLM-EdgeFlow 当前代码、架构、测试、构建发布体系和工程治理进行全面审查的方法、范围、证据要求与验收规则。

本轮审查必须遵循以下原则：

1. **结论后置**：开始审查时不预设 PASS，也不以已有验收报告作为当前结论。
2. **基线冻结**：所有证据必须绑定唯一 Commit、工具链和执行环境。
3. **审查与整改分离**：取证阶段保持只读；问题确认后，再建立独立整改提交。
4. **事实与声明分离**：测试通过只能证明其覆盖范围，不能外推为全量安全、零泄漏或真实硬件正确。
5. **正常与异常并重**：除 Smoke 成功路径外，必须验证失败传播、资源清理、并发竞态和部分完成语义。
6. **可复现**：每项结论都必须能追溯到代码位置、命令、输入夹具和原始结果。

现有
`doc/rfcs/reviews/framework_comprehensive_audit_report.md`
在本轮审查完成前仅作为历史草稿，不得作为验收证据，也不得预先继承其中的 “100% PASS” 结论。

---

## 2. 审查目标

本轮审查回答以下问题：

1. 四层架构的真实依赖方向是否与设计、治理规则和构建关系一致。
2. C ABI 与 Platform Operator 公共接口是否具备稳定契约、异常边界、生命周期安全和兼容性。
3. Pipeline、动态黑板、注册中心和并发调度是否在正常、失败及竞态场景下保持一致状态。
4. 业务节点、公共节点、Adapter 与 Engine 是否职责清晰、请求无状态且不存在隐式跨层耦合。
5. 定长 Batch、Dummy 补齐/剥离和样本溯源是否在所有边界条件下正确。
6. Demo、Profile、配置、数据集和结果文件是否形成可自动验证的端到端契约。
7. CMake、脚本、CI、依赖供应链和发布流程是否可重复、可诊断且不会产生虚假通过。
8. 文档、RFC、Skills 和多 Agent 指令是否与当前代码事实一致。
9. 当前测试覆盖之外还存在哪些未验证风险，能否明确标记为“未验证”而不是推断通过。

| 项目 | 必填内容 |

范围内：

- `include/`、`src/`、`demo/`、`tests/`；

- 非项目声明支持的平台和工具链。

范围外项目必须标记为 `NOT VERIFIED`，不能视为 PASS。

## 4. 风险等级与验收规则

### 4.1 问题等级

| 等级 | 定义 | 示例 | 验收影响 |
| :---: | --- | --- | --- |
| P0 | 可造成安全事故、数据破坏、宿主崩溃或不可恢复状态 | C ABI 异常逃逸、UAF、确定性数据损坏 | 立即 FAIL |
| P1 | 核心功能错误、架构红线违规、生命周期/并发错误 | 双重释放、错误成功、Pipeline 状态污染 | 阻塞验收 |
| P2 | 局部契约、诊断、测试覆盖或可维护性缺陷 | 错误码不一致、关键失败路径无测试 | 可有条件验收 |
| P3 | 非阻塞优化建议 | 命名、重复代码、文档表达改善 | 不阻塞 |

### 4.2 最终结论

- **PASS**：无 P0/P1；全部强制门禁通过；没有关键范围缺失。
- **CONDITIONAL PASS**：无 P0/P1；存在已记录的 P2，且明确责任人、整改条件和复验方式。
- **FAIL**：存在 P0/P1，或强制门禁失败。
- **NOT READY / NOT VERIFIED**：基线不清、关键环境不可用或证据不足，无法签发结论。

测试通过本身不能覆盖静态审查发现；已有问题也不能因正常回归通过而自动关闭。

## 5. 证据与发现记录规范

每个检查项必须输出以下字段：

| 字段 | 内容 |
| --- | --- |
| 检查项 ID | 如 `AUD-L1-ABI-001` |
| 状态 | PASS / FAIL / PARTIAL / NOT VERIFIED / N/A |
| 审查基线 | 完整 Commit SHA |
| 代码证据 | 文件和行号 |
| 动态证据 | 命令、退出码、关键输出 |
| 覆盖边界 | 该证据能够和不能证明什么 |
| 发现编号 | 如 `F-P1-003` |
| 修复建议 | 最小修复范围 |
| 复验条件 | 能在修复前失败、修复后通过的检查 |

所有临时夹具、日志和测试结果写入独立审查目录，不得混入源码目录或提交到仓库。

## 6. 审查工作流

### Phase 0：冻结基线与建立独立环境

1. 记录 Commit、分支、工作区和工具版本。
2. 生成文件、测试、配置、脚本和公共接口资产清单。
3. 在临时 worktree 或干净副本中执行会修改文件的脚本。
4. 分别创建 Release、Debug、ASan/UBSan 和 TSan 构建目录。
5. 将现有综合审查报告标记为历史草稿，不读取其结论作为审查输入。

退出条件：基线唯一、工作区状态已记录、执行目录不会污染用户源码。

### Phase 1：公共契约与高风险生命周期

优先审查最可能造成宿主崩溃或数据损坏的部分：

1. C11 ABI 头文件、导出符号、结构体布局及版本兼容。
2. 六个 C ABI 函数的 `noexcept`、顶层异常捕获和错误码映射。
3. Platform Operator 函数表、公共辅助 API 和错误诊断契约。
4. Handle 状态机、重复 Destroy、DeInit 清理和非法句柄防护。
5. 输入借用、CopyIn、输出分配/释放回调和缓冲区容量规则。
6. C ABI 与 Platform Operator 是否统一委托至同一运行时。

退出条件：所有公共入口均有静态调用链和异常/所有权矩阵。

### Phase 2：Pipeline、黑板和并发状态

1. Pipeline 配置解析、未知字段、路径和数值边界。
2. Build 状态机所有成功、失败和异常出口。
3. DAG 拓扑、成环、重复节点 ID、孤立节点和波前调度。
4. `AlgContext` 类型安全、锁生命周期和错误状态传播。
5. `SessionContext`、ModelManager 和 Engine 生命周期。
6. Process、Control、Destroy、DeInit 的允许并发矩阵。
7. Node/Engine Registry 的重复注册、重入和锁外构造。

并发声明必须由代码同步策略和动态测试共同支撑；普通多线程测试不能替代 TSan。

### Phase 3：业务节点、公共节点与 Engine

1. 穷举所有 `INode` 派生类的成员变量，确认无请求级跨调用状态。
2. 核对 Adapter DTO 与节点黑板 Key、类型、数量和所有权。
3. 检查公共节点是否真正参数化，是否仍隐式绑定单一业务 Key。
4. 检查 Control 热更新的锁、原子性和失败回滚。
5. 核对每个 Engine 实现与能力接口、设备 ID、模型路径和错误码。
6. 验证所有 Batch 实现是否通过 `FixedBatchExecutor::Execute`。
7. 验证 0、1、固定 Batch、非整除、大 Batch、底层失败和输出数量异常。
8. 核对 Dummy 剥离及 `(req_id, sub_id)` 溯源不变量。

MockNPU 只能证明 Mock 契约，不得用于宣称真实硬件时序或 DMA 行为已经验证。

### Phase 4：Demo、配置、数据和结果契约

1. 检查 Demo 是否只依赖公开接口。
2. 验证 Profile Schema、CLI/Profile/default 优先级和 Suite 单一事实源。
3. 遍历所有 `.conf/.json` 对并核对业务绑定、模型覆盖和相对路径。
4. 校验全部语料的编码、字段、必填项和 fallback 策略。
5. 验证成功输出、失败输出、覆盖、追加、原子替换和摘要统计。
6. 注入 Create、Control、Process、Destroy、业务序列化及 Writer 失败。
7. 明确多 Chunk 下已完成、失败、跳过样本的状态和业务输出语义。
8. 从仓库根目录和仓库外目录执行 CLI 与脚本。
9. 分离默认 Smoke 和真实模型路径，真实资产缺失不得伪装成通过。

必须包含以下负向探针：

- 非法 CLI 整数、尾随字符、溢出和未知枚举；
- Profile 根节点、字段类型、Suite 和范围错误；
- `.conf`/`pipe_path`/Pipeline 结构错误；
- Business 与 Pipeline 不匹配；
- 数据集缺失及格式不完整；
- Control 文件缺失、非法或下发失败；
- Process 中间 Chunk 失败；
- 输出目录不可创建、文件不可写和重命名失败。

### Phase 5：构建、CI 与供应链

1. 从干净环境执行 Debug 和 Release 配置/构建。
2. 检查 In-source 构建防护、编译选项、RPATH 和安装/导出规则。
3. 动态枚举并核对全部默认 CTest（当前 23 项）及条件测试的注册、工作目录和超时。
4. 审查 CI 是否检查格式差异，而不是格式化后只执行 `git diff --check`。
5. 审查 `run_all_tests.sh` 是否遗漏 CTest、是否绕过超时、是否输出过时数量。
6. 检查脚本的 `set -euo pipefail`、参数、路径、网络失败和重复执行。
7. 检查 FetchContent 版本固定、URL/hash、License 和离线重建能力。
8. 核对最新远端 CI 的 Commit 是否与审查基线完全一致。
9. 在条件允许时执行 GCC/Clang 与 Linux/macOS 矩阵。

远端 CI 不可访问或 Commit 不一致时应标记为 `NOT VERIFIED`。

### Phase 6：动态安全、压力和性能

#### 6.1 Release 回归

- 干净 Release 构建；
- 全量 CTest；
- LayerGuard；
- Smoke Demo；
- 双 CLI；
- 在隔离 worktree 中执行六阶段脚本。

#### 6.2 Sanitizer

- ASan/UBSan 使用独立构建目录；
- 记录实际运行了哪些测试，禁止用局部结果表述全量安全；
- LeakSanitizer 被关闭时明确写明“未验证泄漏”；
- 支持条件下以 TSan 运行并发、Pipeline、Control 和生命周期测试；
- Sanitizer 不支持第三方引擎时，分别报告项目代码与第三方范围。

#### 6.3 压力与故障

- 多线程重复 Process；
- Process 与 Control 交错；
- 声明支持范围内的 Destroy/DeInit 竞态；
- 多轮 Create/Destroy 资源回收；
- Engine 失败、异常、输出缺失和超时；
- 配置解析器及公共 ABI 非法输入矩阵。

#### 6.4 性能

在没有既有 SLO 时先建立基线，不直接评价“高性能”：

- 单样本及多 Batch 吞吐；
- P50/P95/P99 延迟；
- 峰值内存；
- 顺序与波前并行对比；
- Dummy Padding 开销；
- 结果记录绑定硬件、编译选项和输入规模。

如已有历史基线，应定义允许回退阈值并进行自动比较。

### Phase 7：文档、RFC、Skills 与治理一致性

1. 核对 README、架构图和代码目录。
2. 核对 RFC 状态、设计提交、实现提交和验收报告。
3. 区分历史问题、当前问题和目标设计，避免旧报告冒充当前事实。
4. 核对 AGENTS、CLAUDE、GEMINI、Copilot 指令的优先级和命令。
5. 核对三个项目 Skill 与真实接口、模板和脚本。
6. 搜索硬编码的测试数量、配置数量、版本和过时路径。
7. 验证所有文档链接、命令和示例可执行。

治理一致性单独计分，不得稀释代码安全问题的严重级别。

### Phase 8：出具报告、整改与复验

1. 先冻结只读审查发现，不在发现确认前修改代码。
2. 按 P0/P1/P2/P3 排序，合并重复根因。
3. 为每项问题提供最小复现和建议测试。
4. 用户确认后，在独立分支进行整改。
5. 修复必须增加能够在旧实现失败的新测试。
6. 复验修复项，并重新运行所有受影响门禁。
7. 最终报告同时保留首次发现、修复提交和复验结果。

## 8. 审查报告结构

最终报告使用以下结构：

1. Executive Summary；
2. 审查基线与环境；
3. 范围、排除项和未验证项；
4. P0/P1/P2/P3 发现摘要；
5. 各层静态审查证据；
6. 动态测试与故障探针证据；
7. Sanitizer、并发、性能和平台矩阵；
8. 构建、CI 与供应链；
9. 文档、RFC、Skills 和治理一致性；
10. 整改提交与复验记录；
11. 最终 PASS / CONDITIONAL PASS / FAIL / NOT READY 结论。

报告禁止使用以下无边界表述：

- “100% 内存安全”；
- “零内存泄漏”，但 LeakSanitizer 未运行；
- “全平台通过”，但只运行单一平台；
- “真实硬件验证”，但只使用 Mock Engine；
- “全部代码覆盖”，但没有覆盖率证据；
- “全部问题关闭”，但仍存在未复验或 NOT VERIFIED 项。

## 9. 完成定义

只有满足以下条件，本轮全面审查才算完成：

1. 基线、环境和资产清单已冻结；
2. 所有检查项均有明确状态；
3. 所有 P0/P1 均已修复并复验，或最终结论为 FAIL；
4. P2/P3 均已登记，不因正常回归通过而隐藏；
5. 强制门禁完成，条件性项目明确标记 NOT VERIFIED；
6. 审查和整改提交可区分；
7. 最终报告中的每个结论都有可复现证据；
8. 工作区没有审查工具造成的非预期源码修改。

本方案的目标不是证明框架“没有问题”，而是准确回答：当前基线已经证明了什么、发现了什么、尚未证明什么，以及达到可合并或可发布状态还需要完成什么。
