# 错误码与日志

项目维护两套错误码：框架码定义在 `include/contracts/error_codes.h`，当前平台对外码
定义在 `include/platform_mock/error_codes.h`。内部整数接口沿用 `int`。成功为 0，失败使用
`llm_edgeflow::error::k...`，同一值只有一种含义。Core、Node、Model、Backend 和 Adapter
内部使用框架码，不引用平台错误码。Operator 协议壳是唯一的平台错误映射边界。
公开 C 接口（Operator 函数表和 AlgBase 日志接口）沿用各自的平台或文档化返回约定，
不返回框架码。日志接口的约定由 [日志](../logging.md) 维护。

框架码表同时提供 `ErrorCodeName`，供结构化诊断、CLI 和日志使用。诊断的字段路径、
节点/模型名及原因继续单独传递。不得用统一分类代替具体原因。Studio 的错误名称引用
同一张表，HTTP 状态仍由 HTTP 接口决定。厂商状态留在 Backend 中转换，原始原因保留
在诊断中。

## 实施与验收边界

1. 从框架码表选择与失败原因对应的错误码。
2. 在 Operator 边界按错误含义映射平台码。不要仅按数值相等建立映射。
3. 填写具体原因和诊断上下文。
4. 在测试中核对内部码、平台码、诊断内容和日志等级。

修改错误处理时，保留输出清理、来源编号、Control 回滚、输出池生命周期和异常屏障。
测试应覆盖主动失败、标准异常、未知异常、配置错误和运行时错误。
执行默认门禁。若涉及非默认 Backend，还需构建并验证对应测试。真实推理需要权重和运行环境。

## 日志职责

在错误产生处填写具体原因。在具有完整调用上下文的边界记录日志。
直接转发错误的函数不重复记录。独立入口没有上层日志时，由该入口记录。
平台映射日志包含框架错误名称、内部码、平台码和操作。不要记录完整请求、模型输入或凭证。

沿用 `edgeflow/log.h` 的六级宏：

| 等级 | 用途 |
| --- | --- |
| `ALG_LOG_FATAL` | 运行实例无法继续服务的致命故障 |
| `ALG_LOG_ERROR` | 执行、资源、异常或内部约束失败 |
| `ALG_LOG_WARNING` | 输入/配置被拒绝、可恢复异常或降级 |
| `ALG_LOG_INFO` | 初始化、加载、配置切换等生命周期 |
| `ALG_LOG_DEBUG` | 阶段、数量、容量等排查上下文 |
| `ALG_LOG_VERBOSE` | 按需开启的逐项、逐批次细节 |

按调用场景选择日志等级。错误码表不设置日志等级。
关闭日志后，调用者仍可读取错误诊断。
