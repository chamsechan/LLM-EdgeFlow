# 面向大模型方案开发者的架构定位与实施规划

- 日期：2026-09-06
- 现状基线：RFC-0038 扩展入口及 RFC-0039 开发路径修复；验证范围见第 7 节
- 文档性质：用户诉求整理、架构判断与后续实施规划
- 状态说明：标为“已完成”的内容有当前实现；标为“建议”或“待实施”的内容不构成已交付能力

框架应让方案开发者围绕四件事工作：组合节点、实现缺失算法、转换平台输入输出、
运行同一个 Demo 验证方案。四层架构继续承担调度、资源、类型和生命周期管理，
日常开发入口集中在 Pipeline、Node 和 Adapter。

`src/custom_nodes/` 统一领域算法的源码归属；脚手架、两份可运行样例和统一 Demo 提供
最小开发路径。接下来通过开发者试用检验门槛，并按具体方案完成真实模型和平台验收。

## 1. 用户诉求与约束

### 1.1 已明确的需求

| 编号 | 用户诉求 | 对实现的要求 |
| --- | --- | --- |
| R1 | 主要使用者是大模型方案开发者 | 使用文档和默认入口按方案开发任务组织；维护者知识按需展开 |
| R2 | 将已有 Node 连线构造成方案 | 已有契约与能力下，通过 Pipeline/Studio 完成组合，无需改 C++ |
| R3 | 缺失算法允许在 Node 中开发，也可以复用已有 Node | 支持有领域语义的自定义节点，允许前处理、模型调用、后处理组合 |
| R4 | 用 Adapter 对接平台输入输出结构体 | 结构转换、拷贝、容量和生命周期保持在接入层 |
| R5 | 一个通用 Demo | 共享命令、执行流程和结果输出；新方案尽可能复用已有数据转换 |
| R6 | 降低门槛，保护框架整洁 | 作者集中编写算法与映射，框架封装机械工作和公共约束 |
| R7 | 接受仓库内源码扩展与重新编译 | 优先完善静态注册和构建路径，无需为此引入动态插件 ABI |
| R8 | 用统一 custom Node 目录，避免按业务展开大量文件夹 | 自定义节点按操作组织，允许多个方案复用，不创建每业务目录树 |

用户的典型处理流程是：

> 输入进来，处理逻辑，调用模型，再处理逻辑，再拷贝出去结果。

这里需要区分三种处理：平台结构转换归 Adapter；业务计算、提示词组织和业务结果解释归
Node；tokenizer、模型输入输出语义、张量与推理资源归 Model/Backend。边界清晰后，
业务作者可以用较少的代码表达完整流程。

### 1.2 架构建议与已确认需求的区别

样例、脚手架和 Demo 注册已按第 7 节实施；开发者上手验收仍待执行。文档中的进一步
简化建议不等于已实现接口，应以实际重复成本决定是否实施。

用户接受重新编译，当前目标也没有要求脚本节点、任意模型动态发现、多租户服务或
无代码生成任意平台结构体。后续工作应优先完成现有 C++ 使用路径。

## 2. 当前已经具备什么

可用能力以 `build/alg_pipeline_tool catalog` 为准；测试模型仅出现在开发工具中。
不同 Backend 构建的能力不同，不以文档中的固定数量作为可用性承诺。

| 能力 | 当前状态 | 对目标用户的实际意义 |
| --- | --- | --- |
| Studio 端口连线、模型表单与原生校验 | 已实现 | 已有能力可以在同一套规则下组合、定位错误、保存与试运行 |
| `NodeBase`、类型端口、`ModelBoundNode` | 已实现 | 自定义逻辑可以复用执行入口、异常处理和单模型绑定 |
| `custom_nodes` 的源码与构建入口 | 已完成并提交 | 领域算法有统一归属，与通用节点共用 Layer 3；已有完整作者样例 |
| Adapter、双出口结果打包、Operator bridge 辅助 | 已实现 | 可以接入新结构，部分容量与转换代码已经复用 |
| `alg_demo`、Profile、数据集与结果输出 | 已实现 | 一个程序承载现有业务；新增外部契约仍需要数据转换代码 |
| 完整 custom Node 接入样例 | 已实现 | 同一 PromptGuidedLlmNode 在实体抽取和文档问答中复用，沿用既有 Adapter 与统一 Demo |
| 节点源码脚手架 | 已实现 | 生成真实接口和注册测试片段；受支持模板进入编译与执行测试，领域逻辑仍由作者实现 |
| 真实业务效果与目标环境验收 | 按方案补齐 | 代码回归成功不等于业务效果、性能与部署验收完成 |

Demo 描述符必须给出业务类型，运行器仅从注册表读取；缺失注册或 UNKNOWN 类型会
失败。已有外部契约的新方案只需配置与 Profile；全新外部结构仍需实现 Adapter、
Operator bridge / ValueType 及 Demo 数据转换，不能把“注册无中央分支”理解为自动生成转换。

## 3. 架构目标：按角色暴露复杂度

| 角色 | 主要工作 | 通常需要理解的接口 |
| --- | --- | --- |
| 方案开发者 | 查能力、配模型、连端口、调参数、验证结果 | Pipeline、Catalog、Studio、Demo |
| 算法开发者 | 实现缺失的领域处理和前后处理 | 类型端口、Node、模型能力接口、Definition |
| 平台接入者 | 外部结构转换与结果复制 | Adapter、外部 ABI、Operator 类型和容量契约 |
| 框架与推理维护者 | 调度、资源、模型语义、Backend、公共支持代码 | Core、Model、Backend 和相关运行时契约 |

同一个人可以兼任这些角色。目标是让每次任务只涉及必要的知识，而非强制团队人员分工。
例如沿用已有平台结构、已有模型，仅增加一段业务算法时，作者不应修改 Core、Model、
Backend 或中央业务分发。

运行时继续使用现有链路：

```mermaid
flowchart LR
    Input[平台输入结构体] --> Unpack[Adapter 解包与校验]
    Unpack --> Pipeline[Pipeline 执行计划]
    Pipeline --> Node[通用或自定义 Node]
    Node --> Logic[前处理与业务计算]
    Logic --> Model[声明绑定的模型能力]
    Model --> Post[后处理与结果解释]
    Post --> Value[类型化内部结果]
    Value --> Pack[Adapter 检查容量并打包]
    Pack --> Output[平台输出结构体]
```

图中表示请求执行过程；源码依赖继续遵守 Layer 1 → Layer 2 → Layer 3 → Layer 4。
Node 通过模型能力接口调用推理，Backend 不识别上层业务。

## 4. 源码组织与复用规则

### 4.1 保留当前目录体系

```text
src/
  common_nodes/     框架维护的通用操作
  custom_nodes/     用户编写的领域算法与特定前后处理
  adapter/          平台输入输出转换
  core/             校验、计划、调度和上下文
  engine/           Model 与 Backend
include/nodes/      两类节点共用的浅层支持接口
configs/            方案与部署配置
demo/               统一运行器和数据转换
tests/              按现有组件职责组织的验证
```

自定义节点默认采用一个操作一个 `*_node.cpp`，类实现、Definition 和注册可以放在同一
文件中；只有确有共享声明需求时才增加头文件。Adapter、配置和 Demo 沿用现有位置，
无需复制为每业务一整套目录。

`custom` 是源码归属和维护分类。节点能否复用取决于输入输出语义、类型、参数及模型需求。
默认不把项目名、客户名、固定外部结构体或当前方案的 Blackboard key 写进节点接口。
`biz_names` 仅表达真实业务契约限制，不能因为源码位于 custom 目录就强制绑定业务。

### 4.2 分清三个复用单位

1. **方案复用**：克隆或修改 Pipeline，调整节点连线、模型绑定和配置。
2. **节点复用**：同一个注册 Node 被多个 Pipeline 使用，必要差异由有语义的参数表达。
3. **代码复用**：多个实现共享纯计算或解析逻辑时提取普通函数；不在 Node 内直接构造
   另一个 Node 来绕过端口、计划和调度。

自定义节点不必先达到通用库标准才能使用。已有多个稳定使用方、参数与端口语义清晰，
且有共同维护意愿后，可以评审提升到 `common_nodes`；目录迁移应保留节点类型名和端口
契约。避免“已被两个业务使用就自动升级”这种没有维护收益判断的规则。

### 4.3 防止 custom 目录成为杂物目录

本目录只放 Node 与直接相关的算法实现。外部结构体、模型权重、平台 SDK、复制出来的
通用 Node 和另一个 Pipeline 调度器都不属于这里。

文件按操作命名，注册类型名保持全局唯一。随着数量增长，优先使用 Catalog 搜索和
Definition 描述查找能力。出现真实共享代码后再抽取小型支持模块，不提前按业务、客户
或模型建立多级目录。

## 5. Node 的粒度与边界

### 5.1 同时支持组合与完整领域处理

| 情况 | 推荐方式 | 原因 |
| --- | --- | --- |
| 只是提示词、阈值、规则、模型绑定不同 | 配置已有 Node | 保持修改成本低，避免重复实现 |
| 前处理、推理、后处理需要独立复用或调试 | 多个 Node 连线 | 中间结果可观察，模型与参数可分别替换 |
| 领域步骤紧密相关，独立拆分缺乏收益 | 一个 custom Node 内完成前处理、模型调用、后处理 | 保持业务逻辑可读，减少仅传递数据的节点 |
| 新模型格式、tokenizer、模型输出语义 | 扩展 Model | 使业务 Node 不依赖具体模型实现 |
| 新设备运行时或厂商 SDK | 扩展 Backend，或依真实契约归 Adapter | 保持供应商接口在责任层内 |

一个 custom Node 应代表一个能解释和验证的算法结果。若它包含多个互不相关的产出、
大量独立参数或无法定位的失败步骤，就需要重新评估粒度。

### 5.2 先支持可声明的单模型处理

现有 `NodeDefinition` 使用单个 `model_capability` 和 `model_config_field`，
`ModelBoundNode` 也绑定一个模型。这是当前最短路径的可靠边界。

多个模型参与时，优先使用多个声明清楚的节点组合。若真实需求必须在一个 Node 中
动态选择或调用多个模型，需要先设计可供 Validator 与调度器识别的模型依赖声明。
不得在简化接口中隐藏额外模型获取，使并发、能力与资源冲突检查失去依据。

一对一批处理支持类只适用于输出数量和来源保持一致的操作。切片、过滤、聚合等操作
需要声明真实基数与来源策略，不能为了套模板假设所有算法都一进一出。

### 5.3 自定义算法仍遵守公共运行约束

- 输入通过已解析的类型端口读取，输出通过端口一次发布；请求编号和子样本编号必须保留
  或按声明的转换规则生成，不能按结果位置猜测归属。
- 请求数据放在局部变量或 `AlgContext`。成员仅保存配置或安全共享句柄；
  `parallel_safe` 不能由模板无条件设置为真。
- `NodeBase` 提供异常边界；作者返回有语义的失败。解析回退和模型失败不得被包装为业务成功。
- 业务提示词和结果解释属于 Node；模型的 tokenizer、张量组织与模型输出解释属于 Model。
- Node 不加载厂商运行时，不复制平台指针，不直接创建、调度其他 Node。

### 5.4 新的数据类型应有最小独立契约

优先复用现有中性值类型。确需新类型时，建议把最小字段定义及唯一类型标识放在独立
契约头中，由相关 Adapter 和 Node 引用；Core 保持通用类型存取，不需要认识业务字段。
具体类型按现有风险流程设计，不把所有项目字段都追加进一个全局业务大结构。

新类型必须有一致的 `BlackboardTypeTraits`/端口类型标识、基数和来源语义。
不应为减少声明而统一退化成 `void*`、任意 JSON 或缺少 Schema 的字符串传递。

## 6. 降低开发门槛的实施方法

### 6.1 将常见接入分为三条路径

| 路径 | 必要业务改动 | 可复用的部分 |
| --- | --- | --- |
| A：已有契约、已有节点和模型 | Pipeline 与运行参数；按需增加 Profile/数据集 | Adapter、Node、Demo 执行器 |
| B：已有契约、缺失领域算法 | custom Node、源码登记、节点测试、Pipeline | 模型实现、Adapter、Demo 数据转换 |
| C：全新平台输入输出契约 | 路径 A/B，加外部结构、Adapter、必要的 Operator 类型/bridge 和 Demo 数据转换 | Core、调度器、模型资源、统一 Demo 执行流程 |

“同一契约”包含合法 `biz_name` 和 ingress/egress。复用现有合法业务名可以只改方案；
新增注册业务名或修改输入输出并不自动成为纯 JSON 改动。

### 6.2 先提供最小可运行样例

建议以一个团队实际需要、Catalog 确实缺失的领域算法为样例，完成路径 B：

1. 复用已有外部输入输出与一个已注册模型能力。
2. 在 custom Node 中实现少量明确的业务前后处理。
3. 用同一节点分别编排两个方案，证明节点没有绑定单个业务配置。
4. 接入现有 Demo，提供固定样本、期望结果和一次模型失败示例。
5. 在无权重环境用测试能力验证控制流，在授权的真实模型环境验证算法结果。

确定性替身继续归测试/开发支持目标，不能成为正式 SDK 的假模型。样例应可编译并有
必要测试，避免维护一份只存在于文档、会逐渐失真的大段伪实现。

样例算法还没有被用户指定，本规划不凭空新增一个生产节点。下一次具体实施应先从
实际方案中选择最小能力缺口。

### 6.3 根据样例压缩重复代码

完成样例后，记录作者在端口绑定、Definition、配置校验、错误映射和来源检查上重复
填写的内容。优先改进已有 `NodeBase`、`ModelBoundNode` 和少量辅助函数。

模板可以预置声明结构、注册宏和构建位置；真实语义仍由作者填写。不要同时维护手写
Catalog、Studio 节点表和另一份模板 Schema。需要生成器时，让它输出常规可读的源码，
并由现有注册与 Validator 校验结果。

暂不增加新的深层继承体系或要求所有算法实现固定的三个虚函数。纯处理、单模型推理、
一对多转换的需要不同，现有支持类可以按场景使用。

### 6.4 Adapter 让作者集中填写转换

继续使用 `ResultPackingAdapter` 和现有单槽 bridge 辅助，避免把固定 C ABI 输出与
Operator 可变长结果各写一套业务校验。作者填写外部字段到内部值、内部结果到输出字段
的映射；公共代码负责容量、来源关联、错误和生命周期。

全新宿主结构仍需声明内存类型和所有权，不能通过隐式强转或反射猜测布局。
公共 C ABI 的固定数组上限与 Operator 的输出池容量不同，简化入口必须保留这一事实。
涉及新公开结构或容量语义时，按公共契约变更处理。

### 6.5 将“通用 Demo”落实为稳定执行器

目标保留一个 `alg_demo`、一套参数/Profile、一套执行与结果输出；不同输入输出结构
通过薄的数据转换注册接入。新方案复用已有契约时无需编写新的执行流程；新契约仍需
提供数据读取和输出解释。

Demo 的中央业务名映射已收敛为必填注册描述符。新增外部契约时继续复用
`OperatorBizBridgeDescriptor` 的权威槽位信息，并实现必要的数据转换，不再增加中央
名称分支。现有 Profile 和数据集保持兼容。

Demo 必须经过实际 Adapter/Operator 与 Pipeline 链路。直接调用 Node 适合单元测试，
不能作为平台接入已经跑通的证据。Smoke、真实推理、业务效果检查应有明确的运行模式。

## 7. 分阶段实施与验收

| 阶段 | 优先级 / 状态 | 最小交付 | 完成条件 |
| --- | --- | --- | --- |
| S0：统一扩展归属 | 已完成 | custom 目录、同一 Layer 3 构建、分层检查、接入指南 | 已由 `4117461` 提交，89/89 个 CTest 分组通过 |
| S1：跑通作者闭环 | 工程闭环已验证 | 同一 PromptGuidedLlmNode、两份严格业务配置与 smoke Profile | 原生 validate/plan、统一 Demo 实际执行与内容/来源断言；模型失败故障注入 |
| S2：减少作者重复代码 | 支持范围内已验证 | 脚手架、CMake 登记、打印注册测试片段 | 所有受支持骨架真实编译、注册、类型绑定与执行；非法 CLI / 不适用签名拒绝 |
| S3：补齐新外部契约路径 | Demo 注册已修复；新契约按需 | 删除中央兜底；注册强制业务类型 | 别名无中央改动即可注册；实际新平台结构仍待业务需求驱动验证 |
| S4：开发者试用验收 | P1 / 依赖 S1–S3 | 上手观察记录、阻碍清单、对应修复 | 方案开发者能独立完成 A/B/C 中对应任务，错误可定位，修改范围符合约定 |
| S5：具体方案生产验收 | 按项目安排 | 标注效果、目标设备性能、容量和稳定性证据 | 每个上线方案满足事先定义的指标，完成真实部署接入 |

本次修复的统一门禁通过：90/90 个 CTest 分组成功；11 份生成骨架实际编译，两份
custom Profile 经过原生校验、统一 Demo 和输出断言。详细范围见
[RFC-0039 验证记录](rfcs/0039-custom-node-authoring-closure.md)。

S1 的两份样例证明工程接入，不代表新增领域算法已经达到业务效果要求。S2 的生成器
负责骨架，真实算法、配置声明和领域断言仍由作者维护。S3 遇到公司内部
平台 SDK 时，遵守 RFC-0029，在授权内网完成；外部环境只准备中立扩展入口。
维护者可以在闭环完成后再评估高级能力，避免让动态插件、多模型节点等工作阻塞首批使用。

新增 Node、公共接口或跨层机制仍遵循 [CONTRIBUTING](../CONTRIBUTING.md) 的 RFC 阈值。
本规划不另设审批流程，也不把后续建议自动视为已实现或已批准的接口变更。

## 8. 用什么证据判断“降低门槛且没有变乱”

### 8.1 开发者体验

让一位未维护过 Core 的方案开发者实际完成以下任务，记录首次跑通耗时、修改文件、
求助次数和失败原因。先采集基线，再设置团队接受的时间预算，不提前声称节省比例。

| 验收任务 | 可观察的通过条件 |
| --- | --- |
| 换一个已有模型或修改提示词 | 沿用同一节点实现，通过配置完成并运行样本 |
| 增加领域算法 | 主要改动位于 custom Node、测试、配置及源码登记；无需改框架核心 |
| 将该算法用于第二个方案 | 复用同一个注册类型，无复制算法文件，无固定业务 key 阻碍 |
| 接入新的平台结构 | 修改 Layer 1 和必要 Demo 转换；模型与调度代码不感知平台字段 |
| 定位错误 | 非法端口/参数在校验期可定位；运行错误携带节点、请求和明确失败信息 |

### 8.2 工程质量

每项改动使用最小的现有责任套件覆盖新行为，交付执行一次
`./scripts/run_all_tests.sh`。需要重点验证：

- Catalog 能发现新节点，合法组合能执行，非法类型、配置和缺失模型绑定会被拒绝。
- 两个方案复用同一 custom Node 时没有共享请求状态或错误来源关联。
- Adapter 拒绝重复/缺失来源和容量不足；Operator 失败时不会留下部分输出或失效租约。
- Demo 的新增注册能够驱动真实执行路径，已有 Profile 不回归。
- 分层检查持续覆盖 custom 代码，不能出现通用 Node/Core/Engine 依赖 custom 实现。

### 8.3 业务与部署质量

当前工程已经可以开展方案开发试用。生产可用性需要按具体 Pipeline 判断：
配置合法、模型可加载、业务效果达标、目标环境满足性能和稳定性要求，是不同层面的证据。

现有已标注效果集仅覆盖关键词业务 4 条样本；LLM、OCR、ASR、检索等需要自己的数据集与
指标。当前效果工具的字段精确匹配也不能代替生成质量、语义等价或召回评估。
参考[可验证选择指南](VERIFIABLE_SELECTION.md)。

公司内部 SDK、正式交付打包、仓库外消费和目标硬件验收按
[RFC-0029](rfcs/0029-external-readiness-and-intranet-sdk-migration.md) 在授权内网完成。
本文和 custom 目录的完成都不表示这些环节已经验收。

## 9. 后续实施的决策依据

下一步应先选择一个真实缺失的领域算法，证明“custom Node + 已有模型 + 已有 Adapter +
统一 Demo”能够让新作者完成接入，再决定具体简化哪些接口。

评审每个后续改动时，检查它是否减少作者需要理解和重复编写的内容，是否让相同算法更
容易在第二个方案中复用，以及是否仍能通过现有类型、来源、模型依赖和生命周期检查。
目录数量、基类数量或文档页数本身不作为收益指标。

本规划的稳定目标是：通用组件保持可维护，领域算法拥有直接的编写入口，方案开发者能
通过少量必要改动跑通平台输入到平台输出的完整链路。
