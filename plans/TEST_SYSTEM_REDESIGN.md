## 1. 目标与范围

从“当前产品必须保证什么”重新设计测试，不以旧测试文件、用例数量、测试名称或历史断言为迁移清单。
旧测试不构成必须保留的资产，也不要求逐项证明旧测试与新测试等价。需要保留的是当前仍成立的产品契约。

交付一套能发现主要行为回归、容易定位失败、普通开发者能直接修改的测试体系。
范围包括运行时、业务组件、Operator SDK、CLI/Studio/Demo、必要的构建契约，以及可选真实运行时验证。
不借此次工作修改产品功能、维持已取消的兼容行为，或搭建新的测试平台。

人工维护总量的设计预算约为 **1.4 万～2 万行，中心预算约 1.7 万行**。
这是按职责分配的初步估算，不是已经验证的压缩结果，也不是删测配额。
先用小范围实现校准预算；能够更少则更少，必要覆盖超出预算时说明具体原因。

## 2. 原则

1. **测试当前承诺。** 每个测试应能说明：生产中的什么错误会使它失败。没有当前用途的历史场景直接退出。
2. **完整规则矩阵只归属一处。** 调用层测试自己的接线、错误传播和结果组装，不重复展开下层矩阵。
3. **真实组件必须被执行。** 公共机制通过最小探针触发；具体组件至少有自身行为证据，不能只靠注册成功。
4. **预期独立于实现。** 用明确结果或简单独立关系验证；不调用被测解析器、排序器、转换器计算自己的预期。
5. **先写直接、易读的测试。** 相同流程多次出现后再抽取小 helper；表驱动只用于执行流程和断言形状相同的场景。
6. **按风险选择边界。** 只测试实际支持的输入空间和明确承担的错误处理，不穷举类型、参数、组件之间的笛卡尔积。
7. **失败必须可解释。** 场景具名，报告输入和实际结果；并发测试使用同步点，不靠长时间 sleep 或碰运气。
8. **维护成本也是设计约束。** 不引入通用测试 DSL、自动场景编译器、深层 fixture 继承或“万能”假模型。

不以 100% 行覆盖率、固定用例数量、每函数一个测试作为目标。
不为简单 getter、常量转发、标准库行为、仅用于测试的假算法单独编写业务测试。
异常处理、内存与并发测试集中在真正拥有这些责任的边界，不要求每个业务组件重做一套。

## 3. 从生产职责确定必要覆盖

以下是新体系的需求清单，按行为而非现有文件划分。实施时只在对应模块说明中维护必要的补充，
不建立第二套测试需求数据库，也不要求每个断言关联一个编号。

| 责任归属 | 必须验证 | 调用方只补什么 |
| --- | --- | --- |
| 参数与公共类型契约 | 默认值、必需性、类型和范围、嵌套定位、准备与校验钩子；类型化访问和来源关系 | 实际声明的业务约束、参数传递、生效结果 |
| AuthorNode 与批次机制 | 输入绑定、输出数量/来源/生命周期、失败不发布、模型绑定、控制快照、缓存共享与失效 | 具体 Node 的算法、端口接线、特有控制与缓存语义 |
| Orchestration | Validator 生成正确计划及诊断；依赖、顺序、并发约束；Pipeline 消费计划、执行状态、失败收敛 | 入口能正确传递计划结果与诊断 |
| Model Execution 公共机制 | Model/Backend 选择与协议、资源所有权、批策略、padding 去除、失败清理；Tensor 的形状/类型/大小 | 实际 Model 的预处理、数值语义、输出解释与调用参数 |
| Backend | 每种实际实现的协议与参数接入、资源加载/释放、错误传播；厂商接口隔离 | 可用运行时上的小型执行证据，不复制 Model 算法验证 |
| Integration 公共机制 | 部署路径解析、槽位与行关联、容量与预算、输出池/租约、原子发布、错误映射、异常屏障、句柄生命周期 | Converter 的字段语义和完整外部响应 |
| 业务组件 | 真实 Node、Model、Converter 的正常结果、特有边界和失败；不同业务同载体的独立语义 | 每种对外业务有一条完整请求/响应路径，补有独特风险的组合失败 |
| 工具与 SDK 消费方 | 命令/HTTP 状态、序列化、文件写入事务、编辑保存、生成代码可用；公开头文件可编译链接 | 代表性底层错误的转发，不复刻 Validator 全部规则 |
| 工程与环境 | 测试确实被收集执行、失败可使门禁失败；公开依赖隔离、必要的构建条件、可选真实运行时 | 与具体构建/设备相关的执行证据，明确未运行范围 |

当前完整请求/响应的语义归 Adapter，Demo/Python 不能代为补齐业务协议。
当前统一 JSON 输出仍需逐业务检查字段和状态；共享载体不代表共享业务预期。
动态 Catalog 用于核对目标构建实际存在的能力，不代替业务结果的独立预期。

## 4. 测试如何表达

### 4.1 公共规则：基础对象加具名变更

配置、参数和声明校验使用一个小而有效的基础对象，每行仅声明变更及预期错误。
范围约束通常选择合法代表值、有效边界和边界外值；只有存在特殊数值行为时才增加 NaN、溢出等场景。
对诊断只断言约定的错误码、字段路径和必要上下文，不锁死所有自然语言措辞。

例如参数错误由参数层覆盖类型/范围组合；Validator 验证这些错误能定位到节点参数；
CLI 用少量案例验证 JSON 输出和退出状态。三处承担不同责任，不复制整张错误表。

### 4.2 组件行为：输入和独立预期

Node 测算法与业务参数，Model 测输入构造和输出解释，Converter 测外部字段与完整响应。
同类简单样例用本地数据表；流程不同就保留普通具名测试，不用回调表掩盖差异。
确有相同协议的多个真实实现可以共用 GoogleTest 参数化测试，但不强迫所有组件实现测试适配器。

每个组件都应有独立语义证据，但不要求每个组件测试通用空指针、每种参数类型、全部分配失败和全部异常种类。
公共校验可以被组件绕过、组件存在额外失败路径或资源责任时，才增加对应接入验证。

### 4.3 组合规律：少量可复现生成

对于批次顺序、来源对应、分组、排序等规律，先写清不变量，再用固定种子生成少量不同输入。
失败信息包含种子和输入，能够直接复现。关键边界仍保留明确样例。
默认使用现有语言能力和测试框架；没有实际收益前不引入属性测试库或全项目模糊测试平台。
不变量必须来自契约，不能为压缩代码把任意算法假定为可交换、可逆或线性。

### 4.4 资源与并发：只在责任边界展开

对输出池、共享缓存、注册表、调度与控制快照保留针对性的生命周期、竞争和恢复测试。
验证外部可见的结果、资源归还、无部分提交，以及契约要求的后续可用性。
不是所有失败都要求同一对象可以重试，例如一次性 Pipeline 构建失败应验证其规定的失败状态。

故障注入集中到承担分配、提交或异常拦截责任的操作，复用现有必要工具，不固定内部第几次分配。
代表性不同异常路径分别验证，不为每个业务复制故障扫描。
探针仅负责制造输入、记录调用或注入故障；单独验证探针返回固定字符串没有产品价值。

### 4.5 完整链路与真实运行时：各证明一件事

完整业务测试从 Operator 输入到最终响应，使用真实转换器、Pipeline 和 Node；
不确定的推理依赖可在模型边界替换。检查独立预期、行关联和资源释放，不只检查成功返回。
真实 Model 的语义在模型测试中验证，Backend 的真实执行在对应环境验证。

每个支持的外部业务保留代表性成功路径；多槽位、变长输出、控制、缓存等组合按实际风险补充。
不为同一方案的每份 Profile、每种等价路径、每个可互换模型重复完整端到端矩阵。
对维护中的配置做轻量有效性检查；真实权重的效果、速度和目标设备验收沿用
[现有验证边界](../doc/VERIFIABLE_SELECTION.md)，不纳入普通单测的替代性结论。

## 5. 文件与辅助设施

沿用 GoogleTest、Python unittest 和 CTest。目录表达责任，不要求一个生产文件对应一个测试文件，
也不要求一个测试文件对应一个可执行程序。现有 runner 只因依赖或进程隔离需要而调整。

```text
tests/
  unit/
    contracts/            参数与轻量公共契约
    core/                 Validator、Pipeline、上下文与注册机制
    nodes/                作者机制、批次算法、具体 Node
    engine/               Model、Backend 与执行机制
    adapter/              Converter 与 Integration 内部机制
  integration/            模块接线、Operator 完整业务、Demo
  contract/               SDK 消费方、必要编译与架构约束
  tooling/                CLI、Studio、脚手架等工具入口
  e2e/                    需要真实权重或专门环境的测试
  support/                已有多个使用方的小型辅助设施
  fixtures/               小型稳定输入与独立预期
```

上面是目标职责布局，不为统一目录而先搬文件；实现某个责任组时一并整理其归属。
共享机制只建一份测试，具体组件不再放入公共机制的大文件中。
文件变大时按验证责任拆分，不设置机械行数上限。

辅助代码优先留在使用文件；出现真实重复后再共享。共享部分通常只需要临时资源、最小有效配置、
真实组件调用和简单故障探针。它们不能吞掉错误、计算业务预期，或偷偷初始化不相关的全局运行时。
测试专用注册与生产注册分离；仅作测试使用的夹具归测试目录，Demo 实际需要的替身可留在 `dev_support/`。

CTest 的源码收集和执行入口随责任组维护，保留测试发现检查，防止“编译了但没执行”或空过滤器通过。
不把历史 suite 名单固化成覆盖目标；不要新增一套与 CMake/CTest 并行的注册表。

## 6. 日常维护与运行

| 变更 | 默认维护动作 |
| --- | --- |
| 新增业务 Node/Model/Converter | 在所属文件增加独有行为案例；接入完整新业务时增加一条 Operator 路径 |
| 修改共享规则 | 更新规则所属矩阵；只为受影响且有独特风险的调用层补案例 |
| 修复当前产品缺陷 | 在最小能复现缺陷的真实入口保留一个具名案例，能合并就不再复制整条链路 |
| 调整参数或更换兼容模型配置 | 检查有效配置与实际生效结果，不重新生成整套通用测试 |
| 删除功能或改变契约 | 同时删除或改写对应测试、夹具、注册和引用，不保留“历史兼容”空壳 |
| 仅重排代码或修改文档 | 运行适当验证，不因产生 diff 就新增测试 |

评审只需要能回答：覆盖了什么当前行为；属于哪一层；预期是否独立；是否重复验证已有规则。
不新增审批流程、测试数量 KPI、逐断言覆盖台账或日常全量变异测试要求。

开发时运行受影响的最小测试集合；交付沿用唯一入口 `./scripts/run_all_tests.sh`。
默认门禁包括确定性运行时、工具与必要工程契约，不下载大型模型、不依赖内部 SDK。
内存、所有权、并发路径变更按现有 CI 和专项入口运行适用的 sanitizer 检查；
真实 Backend/权重验证按构建与资产条件运行，并报告跳过原因，不用无资产的成功空跑代替执行。
本计划不另外增加日常强制全量检查或重复门禁。

覆盖率只辅助找遗漏，不作为比例竞赛。新体系建立时，对关键责任各选择有意义的错误进行少量故障注入，
必要时在可丢弃的工作区临时破坏实现，确认测试确实能检出；不建设变异测试服务，也不设全局分数门槛。

## 7. 规模预算与统计口径

| 责任组 | 初步预算（行） |
| --- | ---: |
| 公共参数、AuthorNode、批次、Blackboard、注册与共享资源机制 | 3,000～4,000 |
| Orchestration 计划与调度 | 1,800～2,800 |
| 具体 Node 与 Model 语义 | 2,000～3,000 |
| Integration、Converter、Operator 内部机制 | 2,000～3,000 |
| Backend 协议与可选真实运行时 | 1,000～1,800 |
| 工具、Demo 特有行为、SDK 与必要工程契约 | 1,800～2,800 |
| 完整业务链路 | 600～1,000 |
| 共享夹具、场景数据与测试配置 | 1,200～1,800 |
| **合计** | **13,400～20,200** |

同一代码只统计一次；例如共享资源测试归公共机制，具体业务缓存语义归组件。
统计所有人工维护的测试源码、helper、假模型、文本场景、测试专用脚本、生成器及 CMake 配置，
包括放在 `tests/` 之外的测试支持代码；计入注释和空行，避免靠压行制造收益。
已被计入的共享 Demo 替身只算一次。通用生产工具不算测试源码，其测试仍计入。

第三方库、构建产物、生成输出和二进制模型资产不计入人工维护行数；生成器与手写模板必须计入。
资产大小另列，不将大批手工预期搬到未统计目录或压缩文件。
实现后报告范围、总行数和主要分布；不承诺保持现有用例数，也不先规定必须删除多少行。

## 8. 实施顺序

每阶段从当前生产契约出发，完成对应责任组的新测试，同时移除该组被取代的旧测试与无用辅助代码。
不要求照搬旧断言，不长期维护两套体系，也不先清空全部测试再补写。
未处理责任组可暂时沿用原有门禁，直到本组完成替换；这只是实施期间的工作连续性，不是最终保留条件。

| 阶段 | 工作与产物 | 阶段完成条件 |
| --- | --- | --- |
| 1. 验证写法与预算 | 从参数校验、一个具体 Node、一个完整 Operator 业务各选小范围重写；使用普通测试和本地数据表 | 行为来自当前契约，失败可定位；辅助设施小于其带来的重复消除收益；用实际成本校准预算 |
| 2. 公共机制与编排 | 建立参数/作者/批次/资源的唯一规则矩阵，覆盖 Validator、Pipeline 及关键生命周期和并发责任 | 当前关键规则有明确验证归属；代表性错误能被检出，适用的资源检查通过 |
| 3. 组件与业务 | 按当前实际能力完成 Node、Model、Backend、Converter 语义，收敛 Operator 完整业务路径 | 每个支持组件有自身行为证据；业务响应独立验证，调用层没有重复完整公共矩阵 |
| 4. 工具与收尾 | 完成工具入口、SDK 消费方、必要构建与可选环境测试；清理失效 helper、CTest、脚手架和引用 | 新体系按当前责任完整运行，发现/失败传播有效；全局门禁通过，预算与未验证环境如实报告 |

各阶段只增加完成当前验证所需的辅助设施；遇到反复特判的公共 helper，应拆回局部测试。
未达到行为验收时修正本阶段，不靠跳过失败测试或减少明确契约继续推进。
生产契约存在歧义时先明确该具体行为，不扩展成整套框架重构。
阶段交付与分支衔接遵循 CONTRIBUTING；回退以该阶段的 Git 变更为单位，不把历史测试副本长期留在仓库。

### 8.1 提交节奏

采用“完成一个小的验证责任 → 运行相关检查 → 保存一个本地 commit → 开始下一项”的节奏。
阶段不是 commit：一个阶段可以包含多个小提交，不等阶段结束才提交全部代码。
下表同一行列出多个责任时，逐项完成、逐项提交，不将整行合成一个大提交。

- 一个实现 commit 包含该责任的新测试、被替代旧测试的删除、必要的小 helper、CTest 注册和直接受影响的引用。
  不拆成“先删旧测试”和“下次补新测试”两个无法独立验证的提交。
- 每个检查点应能构建并执行对应测试，工作区中不遗留本步骤未完成的配套改动。
  检查失败时先修正当前步骤，不继续堆积其他模块的修改，也不用空壳或 skip 获得通过。
- 按明确文件暂存，检查 staged diff 后提交。提交标题写清具体责任，正文记录实际验证命令、结果和必要的未验证项。
  例如 `test(nodes): replace text chunk behavior tests`，避免只写“继续重构”。
- 如果一个提交需要分别解释几个互不相关的行为，或者修改多个不相关组件，应在编码前拆开。
  不设机械行数限额；删除大段被替代代码可以较多，但新增逻辑必须集中、可审查。
- 提取共享 helper 时在同一提交中带上实际使用方；不先提交一套尚无人使用的测试基础框架。
  独立重命名只有在确实能简化审查、且提交本身仍可运行时才单独保存。

### 8.2 按顺序实施的 commit 检查点

| 顺序 / 阶段 | 做到哪里保存 commit | 提交前的主要验证 |
| --- | --- | --- |
| 0. 方案基线 | 保存本计划及入口链接，生产代码与测试实现不变 | 文档链接和本次交付门禁 |
| 1. 阶段 1：参数试点 | 完成一组标量参数规则的具名数据表，替换对应旧用例及专用辅助代码 | 合法值、边界、非法值及诊断均能实际执行 |
| 2. 阶段 1：Node 试点 | 完成一个真实 Node（优先 `text_chunk`）的独立预期与边界测试 | 执行真实 Node，检查结果、来源及特有失败 |
| 3. 阶段 1：业务试点 | 完成一个 Operator 业务（优先关键词匹配）的完整请求/响应测试，并将实际成本用于校准预算 | 真实业务链路、独立响应预期和输出释放；阶段结束运行完整门禁 |
| 4. 阶段 2：公共机制 | 分别完成嵌套参数、typed Blackboard、共享资源、注册机制、作者输入输出、控制快照、批次算法；每个责任各自提交，过大时再按独立行为拆分 | 对应规则矩阵及该机制的实际调用；涉及资源或并发时运行适用专项检查 |
| 5. 阶段 2：编排 | 分别完成配置诊断、依赖与执行计划、执行状态与调度；不把全部 Core 测试放进一个提交 | 正确计划、错误定位、失败状态；调度变更验证代表性并发路径，阶段结束运行完整门禁 |
| 6. 阶段 3：Node | 每完成一个剩余 Node 的语义测试并移除其冗余矩阵，保存一个提交 | 该 Node 的真实行为及依赖的共享契约 |
| 7. 阶段 3：Model | 每完成一个 Model 的预处理、输出解释与参数接入测试，保存一个提交 | 独立数值/结构预期、实际协议调用及特有失败 |
| 8. 阶段 3：Backend | 每完成一种 Backend 的协议与生命周期测试，保存一个提交 | 当前可用构建的实际实现；需要权重的检查如实记录执行或未验证 |
| 9. 阶段 3：Integration 机制 | 分别完成部署与路径、槽位与错误传播、输出池与租约、发布与句柄生命周期；每个责任各自提交 | 对应机制的结果、所有权及失败状态，运行适用的资源检查 |
| 10. 阶段 3：Converter 与业务 | 按业务完成字段转换和完整响应；Converter 与 Operator 测试较小时一并提交，较大时各自形成可运行提交 | 该业务独立字段预期与完整外部请求/响应，阶段结束运行完整门禁 |
| 11. 阶段 4：工具 | CLI 按命令职责、Studio 按用户操作分别提交；Demo、脚手架各自提交，生成器改动与生成结果验证同次完成 | 真实入口、状态/序列化或文件事务；生成代码可编译执行 |
| 12. 阶段 4：工程契约 | SDK 消费方、构建依赖、测试发现与失败传播按独立契约分别提交 | 编译/链接证据或实际门禁失败信号，取消历史名称清单依赖 |
| 13. 阶段 4：收尾 | 汇总规模、更新维护指南和剩余引用，删除本计划；不在此时集中补交前面遗漏的大批实现 | 完整默认门禁及适用专项验证，确认剩余改动仅属于收尾 |

这是一组提交边界，不预先规定 commit 总数。一个组件过大时继续按可独立运行的行为拆分；
不存在或已在前面完成的责任不制造空提交。跨模块依赖先完成被依赖的共享机制，再调整使用方。
每次阶段交付只在本计划保留简短的当前进度和下一检查点，详细经过由 Git 提交记录承担，不追加日志文档。

### 8.3 检查点与交付的区别

本地检查点运行受影响的构建和测试；只有改变测试收集/过滤时才补对应发现检查。
不要求每个小 commit 都重跑全项目。阶段对外交付或本地交接前，运行 CONTRIBUTING 规定的唯一完整门禁；
已有同一版本的成功结果无需重复执行，之后再有修改则重新验证受影响范围并遵守交付门禁要求。
提交不能被描述为全部验收完成，未执行的专项环境要明确说明。

本地保存 commit 不等于上传、创建 PR 或合并授权。远端交付按用户授权和 CONTRIBUTING 执行；
需要依赖前一阶段的下一交付分支，在前一阶段合入且主线 CI 通过后再从最新 `main` 建立。
暂停工作时应停在已验证、已提交的检查点；恢复时从下一项继续，不再次积累整轮未提交改动。

## 9. 最终验收与文档收敛

完成的判断是当前产品有足够且可维护的验证，而不是文件搬完、测试数不变或行数达标。

- 第 3 节各项当前责任有测试归属，实际组件和完整业务入口均有必要证据。
- 新测试预期独立，失败可复现；没有仅验证假实现的伪覆盖或未执行的空入口。
- 公共矩阵不在各业务重复展开；共享代码简单、局部可理解，没有新测试框架。
- 完整默认门禁及适用的专项验证通过；真实模型、内部 SDK、目标硬件的未验证范围明确。
- 移除被替代文件、失效夹具和历史名称清单；脚手架只生成最小业务测试，不复制通用错误矩阵。
- 将最终职责、写法和运行方式写入 `tests/README.md`，更新相关开发指南，删除本计划；不另建长期历史报告。

首次替换完成后，新增测试仍使用同一原则。没有新功能或风险变化时，不定期追加“兜底测试”以追求数量。
